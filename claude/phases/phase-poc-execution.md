# Phase: PoC Execution & Verbose Verification Report

> **Status: optional, advanced, and NOT part of the enforced `/nightfalcon:nightfalcon`
> pipeline.** The standard review (phases 0–8) never invokes this phase;
> it produces PoC *scripts* (phase-6) but does not run them. This document
> describes an out-of-band workflow for an operator who wants to actually
> execute those scripts against a non-production target they are
> authorized to test. Several steps below reference environment-specific
> helper scripts (`scripts/refresh-auth.sh`, `scripts/discover-service-hosts.sh`,
> `scripts/idor-baseline-retest.sh`, `scripts/classify-poc-run.py`) that are
> **not bundled** with the plugin — they depend on your target's auth and
> ingress specifics, so you must supply them. Only the report renderer
> (`scripts/report/build-poc-execution.py`) ships. Run PoCs only against
> systems you own or have explicit written authorization to test.

You are executing the proof-of-concept scripts generated by phase-6
against a non-production environment, then producing a single-file HTML
report in the **verbose 3-bucket format** (CONFIRMED / BLOCKED / UNTESTED)
where every finding card is readable by a non-engineer.

## Verification bar

A finding is **CONFIRMED** only when the test reached the live target
from outside and the response/DOM directly demonstrates the attack
working. Source-grep matches, gateway 401/403/404, and
hardcoded-credential findings are **not** CONFIRMED — they are
CODE-PATTERN-ONLY / GATEWAY-* / EXCLUDED respectively.

## Workflow

1. Refresh auth from the two browser sessions (attacker + victim) into
   `proof_of_concept/poc-config.env` via `scripts/refresh-auth.sh`.
2. Discover per-service ingress hosts via
   `scripts/discover-service-hosts.sh` (probes candidates, picks first
   with `x-spanid`).
3. Run all `.sh`/`.py` PoCs via `proof_of_concept/run-all.sh` (with
   `POC_ALLOW_WRITE=1` for mutation tests).
4. Run the cross-tenant IDOR baseline via
   `scripts/idor-baseline-retest.sh` with verified-real victim entity IDs.
5. Run browser-driven PoCs (postMessage, open-redirect, storage-trust,
   guest-route, stored-XSS-with-setup) via chrome-devtools, recording
   each result in `proof_of_concept/results/<TAG>/browser-poc-results.jsonl`.
6. Classify every PoC via `scripts/classify-poc-run.py <TAG>` →
   `classification.jsonl`.
7. Render the report via the plugin's
   `scripts/report/build-poc-execution.py <TAG> <DATE>` from the
   workspace root.

## Card format (every finding)

The report's per-finding card has these sections, in this order, with
**no truncation** of any field:

| Section | Source | Plain-English requirement |
|---|---|---|
| **Status pill** | `run_status` → CONFIRMED/BLOCKED/UNTESTED | — |
| **Business Impact** | finding's full `what_happens_md` | Multi-paragraph "what an attacker gains" — never truncate |
| **What we did — step by step** | Hand-authored numbered narrative for CONFIRMED; auto from log STEPs + browser narrative + `attack_steps_md` otherwise | Numbered steps a non-engineer can follow. NO `dispatchEvent`/`pushState`/`curl` syntax — say "we sent the page a browser message pretending to come from an attacker website", "the browser automatically navigated to the destination we put in the URL". |
| **Actual request / payload sent** | `[req]` log lines + browser action payload | The exact technical payload (code block) — engineers need this; lay readers can skip. |
| **Actual response observed** | full `.body.txt` (8 KB) + `[rsp]` lines + browser DOM/network state | Dark-terminal block; full response, not an excerpt. |
| **Why this proves the risk** | browser `why` + classification `why` + reviewer note + finding `severity_md` | The logical connection: "the response contains X, which proves Y, because Z". |
| **What blocked it** *(BLOCKED only)* | classification `why` | And why that is environment, not a code fix. |
| *(collapsible)* How the full attack works | finding's full `attack_steps_md` | — |
| *(collapsible)* Where in the code | finding's `location` | — |
| *(collapsible)* How to fix it | finding's full `fix_md` | — |
| *(collapsible)* Script verdict block | raw `┌─ VERDICT ─┐` from log | — |
| Log path | relative path to `F-NNN.log` | — |

The summary tab shows each CONFIRMED finding as a **full expanded card**
with all sections inline — never a one-line table row.

## Hand-authored "What we did" narratives

For every CONFIRMED finding, write a numbered plain-English narrative
in `HUMAN_WHAT_WE_DID` (a static map in the builder script). Each step
answers: as who? what did we send? what did the system do? what does
that mean? Example:

> 1. As a signed-in admin, we opened the admin console page and waited
>    for it to finish loading.
> 2. We sent the page a browser 'message' stamped as coming from a fake
>    attacker website. Inside the message we put our own URL parameters.
> 3. The page should have ignored a message from an unknown website.
>    Instead, it accepted the message, opened a side panel, and built an
>    embedded iframe page using OUR parameters.
> 4. We inspected the embedded page's address and confirmed our
>    attacker-supplied text was appended verbatim onto a trusted app URL.
> 5. This means any website that can send a message to the victim's
>    app tab can choose what the embedded frame loads.

## Output

`<WORKSPACE>/output/poc-execution-results-<DATE>.html` — single-file,
self-contained, ≤1 `<script>` / ≤1 `</script>`, `</script`-safe JSON
